# Environment egress credentials

Sandpi models outbound credentials as Environment-owned configuration. One v2
Environment owns one Sandbox and one native coding-agent terminal, so its
processes share the same network policy and credential bindings. The selected
native agent and its provider login are separate Environment settings; native
agent credentials use the memory-backed projection described in
[Native agent terminal authority](./native-agent-terminal-authority.md), not
Sandbox0 egress injection.

## Authority boundaries

Three stores have distinct responsibilities:

| Store | Authority |
| --- | --- |
| Sandpi PostgreSQL | User and Environment ownership, display name, desired projection and destination rule, enabled state, reconciliation status and observed source version |
| Sandbox0 credential source | Write-only secret material and its native version |
| Sandbox0 Sandbox policy | The active traffic rules, credential rules and bindings for the shared Environment Sandbox |

Sandpi PostgreSQL has no column for a token, password, certificate, private
key, passphrase or encrypted egress secret. A create or replace request carries
material directly from the authenticated browser request to Sandbox0, then
discards it. Read responses expose neither the material nor the Sandbox0 source
reference.

The Sandbox0 deployment key is not a Sandpi user identity. Before any
credential-source SDK call, Sandpi authorizes the requested Environment against
its own user-owned record. Source names are generated by the server from a
random Sandpi credential id. Sandpi never accepts a source name from a browser
and never lists the deployment's credential sources; reconciliation performs
single-source reads for known Environment records only.

## Supported projections

| Sandpi projection | Sandbox0 source resolver | Protocols |
| --- | --- | --- |
| HTTP headers | `static_headers` | HTTP, HTTPS, gRPC |
| Request placeholder substitution | `static_headers` | HTTP, HTTPS, gRPC |
| mTLS client certificate | `static_tls_client_certificate` | TLS |
| Username and password | `static_username_password` | SOCKS5, MQTT, Redis |
| SSH proxy | `static_ssh_private_key` | SSH |

Resolver kind is immutable. Changing credential type requires creating a new
credential, which prevents an existing binding from briefly interpreting a
source version as another material shape.

## Lifecycle

All mutations run under the Environment lifecycle lock and require a ready
Environment. Its shared Sandbox may be running or paused.

1. Create persists a secret-free pending record, creates the generated
   Sandbox0 source, records its metadata and applies the complete Environment
   policy.
2. Edit and enable/disable update desired configuration, then reapply that
   complete policy.
3. Replace secret updates only the known source and records its new version.
   Sandbox0 advances existing bindings by source name, so a paused Sandbox does
   not need a policy replay. A missing known source is recreated under the same
   generated name and the policy is then reapplied to restore its binding.
4. Delete marks the credential as deleting, reapplies the policy without its
   rule and binding, deletes the source, then removes the Sandpi record.
5. Environment deletion removes the Sandbox before deleting known sources, so
   no live binding can retain them.

Failed work retains a provisioning, error or deleting record. On server start,
reconciliation reads only those known references, repairs the full policy and
finishes pending deletion. Missing source material is never invented or copied
from another source; the UI asks the owner to replace it.

Environment provisioning takes the same cross-server lifecycle lock and
rechecks the pending record after acquiring it. This prevents overlapping
Sandpi rollouts from claiming two Sandboxes for one Environment.

## Complete policy composition

The Environment's default mode and domain exceptions are not a separate update
path from credentials. Every claim and policy update compiles one complete
desired document:

- the base allow-all or block-all mode;
- domain exception traffic rules;
- one credential rule and binding for each enabled source with a current
  version;
- a paired allow traffic rule for each enabled credential when the base mode is
  block-all.

HTTPS, gRPC and mTLS projections request TLS terminate-and-reoriginate. An empty
credential set is sent as an explicit empty binding list, while a normal
Network settings edit loads current Environment credentials before compiling.
This prevents later network edits from silently clearing authentication.
